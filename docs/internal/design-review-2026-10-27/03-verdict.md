# 校园网工具箱 v1.3.2 产品分析

**结论：REDESIGN——重做以“判断网络问题并完成可核对修复”为中心的主流程，保留现有诊断、代理验证和备份基础。**

十原则设计审查为 13/30。问题集中在任务组织、状态可信度和诊断后的行动；单独添加路由勾选框和更改刷新频率不足以解决它们。这里的重做不预设更换 PowerShell/WinForms，也不要求推翻已有实现。

## 用户现在为什么会觉得难用

用户打开它时，需要知道：能不能上网，卡在连接/认证/DNS/代理哪一段，应该点什么，点完有没有改善。当前首屏用代理模式、网卡参数、10 个平级功能、空曲线和日志回答这个需求，用户仍需自己承担排障判断。对已经会排障的人，它是一组工具；对普通校园网用户，缺少从问题到处理结果的完整路径。依据：[E1–E3](01-evidence.md#e1用户任务与界面结构)。

界面已有一致配色、合理的常规字体、六种基本状态和明确的部分权限/备份边界。视觉上有字号、对比度和缩放问题，但这些不足以解释全部体验缺陷，不能只换皮。依据：[E9](01-evidence.md#e9视觉可达性与状态)。

## 对用户补充方案的判断

### 路由守卫的选项

逐项选择、显示后果、备份、复检和撤销的方向成立，但必须先修正检测依据。建议每项展示“发现的证据 → 拟改的对象与值 → 影响 → 应用结果 → 撤销此项”。

“跃点1→9000”仅是某种优先级变化，不保证断网时不走这块网卡；“没有固定校园路由”也不是故障证据。固定路由至少要确认完整目的前缀、当前接口、下一跳和适用网络。方案里的缩写网段不能直接转成实际写操作。现有网络备份没有通用静态路由记录，逐项回滚需要与具体动作一起设计。依据：E3–E4、E10。

默认先不勾选会改变路由的项；用户先看到明确后果。只有真实高频问题及可验证动作进入这一轮，低概率例外先征求用户意见。

### 事件驱动状态栏

方向可以采用，但需要纠正性能依据：149ms墙钟耗时不等于149ms CPU；149/5000不能直接证明常驻3%。6ms/30秒也不是0.012%，并且这个比值仍不是CPU测量。“事件成本0”“必然即时发现断网”和“改后0.01%”都应撤回。依据：E5–E6。

建议先统一状态的含义，再设计调度：网卡/IP变化促发检测，轻量心跳补漏，质量检测按确实需要的状态变化、手动请求和兜底间隔触发；所有需要等待的检测放到后台，界面只显示结果。外网断而网卡仍Up时，不应切换成“稳定在线”；代理软件在别处改变系统代理时也要有更新路径。

30秒和60秒可以作为待测的初始参数，不能同时承诺准确抓到所有10秒中断。监测关闭/保守/标准/灵敏四档先后置，先交付一个行为可解释、结果可靠的默认方案，避免把尚未验证的内部调度参数交给用户选择。

## 主界面的目标

首屏展示一个明确结论、其证据时间、一个主要下一步。例如“已连校园WiFi，需要网页认证”对应“打开登录页”；“手动代理指向未响应端口”对应“查看并关闭此代理”；“外网已验证可用”对应简明状态。不能证明原因时，显示检测范围和下一步检查。

主流程为“检测 → 结论与证据 → 用户选择处理 → 结果对比 → 撤销本次操作”。高级网络参数、完整日志、手动DNS测试和历史图表按需展开或移到次页。代理工具可继续保留独立入口，但不应支配所有用户的首屏。

## 实施前的验收边界

- 用已联网、需要认证、代理异常、网卡正常但外网失败、检测未知五类常见情境核验首屏和下一步。
- 验证已联网点击登录不会因该分支改代理或DNS；无证据的路由建议不可默认为选中。
- 验证备份失败不写系统，部分成功逐项显示，失败记录可重试，恢复仅作用于所选改动。
- 用时间线样本核对10秒附近、两次采样之间中断和工具维护窗口；所有视图同口径，明确无法观察到的范围。
- 同机同配置比较在线空闲、断网、最小化三种场景的CPU累计时间、相关子进程、检测次数和界面响应。此项是未来验收，不是本次已经得到的性能结果。
- 不因本审查为低概率场景添加新框架；入口统一校验一次，不重复判空，不堆空catch，一次性逻辑保持直写。涉及低概率额外处理先征求意见。
